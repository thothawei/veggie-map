### 明確**沒有**的東西（這一批要處理的缺口）

1. **命中原因只說得出一種。** `RestaurantResource` 只有 `matched_menu_items`。
   命中料理種類、地區、描述、飲食類型、或命中的是同義詞變體時，畫面說不出理由。
2. **同義詞展開是隱形的。** 搜「珍珠奶茶」會一併搜「手搖飲」，但結果頁不會說。
   todo.md 自己在 2026-08-27 那一則就點名了這件事，一直沒做。
3. **零結果是死路。** `emptyMessage` ＋ `emptySuggestions` 是**靜態文案**，
   不知道放寬哪一個條件會有東西。
4. **沒有真的錯字容錯。** todo.md 標題寫「錯字容錯」，實作是把 `素时` 這種寫法
   硬加進同義詞表——那是**列舉**不是容錯。真的打錯（`vegitarian`、`素時`、
   片假名打錯一個字）仍然是 0 筆。
5. **搜尋範圍不是控制項，是兩行小字。** 首頁「不限目前範圍」、列表頁
   「會跨全部城市」，兩頁行為不同、都靠一行 hint 解釋，使用者改不了。
6. **建議清單不能用鍵盤。** `SearchBox` 的候選只有 `@mousedown`，沒有 ↑↓／Enter，
   沒有 `role="combobox"`／`aria-activedescendant`。鍵盤與讀螢幕使用者走不到。
7. **沒有最近搜尋。** 輸入框 focus 時空的。
8. **沒有人知道使用者搜不到什麼。** 零結果查詢沒有任何紀錄，
   所以下一輪要加哪些同義詞只能靠猜——這跟這個 repo「先量再改」的作法互相矛盾。
9. **`LIKE '%…%'` 的天花板沒有被量測守住。** 目前資料量小（前幾輪 1159 筆）沒問題，
   但 8 個變體 × 7 個欄位 ＋ 2 個 `whereHas` 是線性成長，沒有任何測試會在變慢時變紅。

## 二、搜尋強化（A1–A9）

排序原則：**先讓已經找得到的東西被解釋清楚**（A1–A3），再讓找不到的東西找得到
（A4），最後才是基礎建設（A8、A9）。這個順序不是隨便排的——A4 的錯字容錯要能
判斷「有沒有變好」，得先有 A8 的零結果紀錄。

### A1 — 命中原因說得出全部，不只菜色

**現況**：`RestaurantResource` 只有 `matched_menu_items`。

**做什麼**：`RestaurantRepository::search()` 在有關鍵字時多帶一個 `matched_reasons`，
每筆是 `{ type, value, term }`：

```text
type   name | menu_item | cuisine | locality | description | diet
value  實際命中的字串（店名片段、菜色名、料理標籤…）
term   命中的是使用者打的哪個詞（展開後的變體，見 A2）
```

`matched_menu_items` **保留不動**（已在 OpenAPI 與前端測試裡，移掉是破壞性變更），
新欄位並存；下一輪確認沒人用了再談移除。

**為什麼**：權重表已經知道「為什麼這家店排在這裡」，只是沒把它說出來。搜「拉麵」
排第一的店如果店名沒有「拉麵」，使用者會覺得排序壞了——其實是命中了料理種類標籤。

**驗收**：搜一個只會命中料理種類的詞，卡片顯示「料理種類：日式拉麵」。
**反向驗證**：把 `cuisine` 那一支從 reasons 拿掉，對應測試要紅。

### A2 — 同義詞展開要看得見，而且可以關掉

**現況**：`KeywordSearch::expand()` 的結果只在 SQL 裡用，回應不帶。

**做什麼**：
1. 搜尋回應的 `meta` 帶 `expanded_terms`：`[{ term: '珍珠奶茶', variants: ['珍奶','奶茶','手搖飲',…] }]`
   ——只列**真的用到**的變體（`max_variants` 截斷後的那些），不是整組詞表。
2. 結果頁頂部一行：「也一併搜尋了：珍奶、奶茶、手搖飲」，每個變體可點（換成搜那個詞）。
3. 新增 `exact=1` 參數：只用原詞，不展開。那一行旁邊放「只搜「珍珠奶茶」」。

**為什麼**：展開是這個專案搜尋能力最有價值的一塊，但使用者看到店名叫「綠意茶飲」
的店排第一時只會覺得搜尋不準。說出來，它就從「怪怪的」變成「原來它懂」。
`exact` 則是給展開幫倒忙時的逃生門（搜「麵包」不想看到麵店）。

**驗收**：`?keyword=珍珠奶茶` 的 meta 有 variants；`?keyword=珍珠奶茶&exact=1` 的
結果數 ≤ 不帶時。
**反向驗證**：讓 `exact=1` 不生效，「結果數應嚴格變少」那條測試要紅。

### A3 — 零結果給「放寬哪一個條件會有幾家」

**現況**：`emptyMessage` ＋ `emptySuggestions` 是靜態文案，只依「有沒有關鍵字」分支。

**做什麼**：0 筆時後端**依序**重跑幾個放寬版本的 `count()`（不是重跑整個查詢，
只要 count），回 `meta.relaxations`：

```text
[{ drop: 'open_now',    label: '不限營業中',        count: 12 },
 { drop: 'venue_scope', label: '包含素食友善店',    count: 34 },
 { drop: 'confidence_min', label: '不限可信度',     count: 51 },
 { drop: 'bbox',        label: '搜尋全部城市',      count: 8  }]
```

只回 `count > 0` 的，最多三項。前端把它們渲染成**可按的按鈕**，按下去就是把那個
條件從網址移掉。

**成本控制**：只在結果為 0 時才算，而且每個放寬版本是一次 `COUNT(*)`（沒有排序、
沒有 eager load）。若量測顯示超過 150ms，就砍成只算前兩個。**先量再定**。

**為什麼**：零結果是搜尋體驗最貴的一刻，使用者當下的問題不是「沒有店」而是
「我做錯了什麼」。四個篩選任一個都可能是兇手，叫他自己一個一個試等於叫他放棄。

**驗收**：開「營業中」＋一個半夜的時段搜到 0 筆，畫面出現「不限營業中（12 家）」
按鈕，按下去真的有 12 家。
**反向驗證**：讓 `relaxations` 永遠回空陣列，前端那條測試要紅。

### A4 — 真的錯字容錯：「你是不是要找…」

**現況**：`素时` 是硬寫在同義詞表裡的一筆。真正打錯的字仍然 0 筆。

**做什麼**：**只在結果為 0 時**才啟動的第二段查詢，而且**不自動改寫**：

1. 候選集合不是整張表，是三份小清單：`restaurants.name`、`CuisineCatalog` 的 label、
   `districts` 的不重複值。（前幾輪的量測是 1159 家，這個規模在 PHP 端算完全可行；
   資料量長大時改成只取同 bbox 內的候選。）
2. 相似度：ASCII 用 Levenshtein（`levenshtein()`），CJK 用**字元 bigram 的
   Jaccard 相似度**——`levenshtein()` 是 byte-based，對 UTF-8 中日文會給出無意義的距離，
   這是很容易踩到的坑，要寫在註解裡。
3. 門檻過了就回 `meta.did_you_mean = [{ term, score }]`，前端顯示
   「找不到「素時」。你是不是要找 **素食**？」——**使用者要自己點**。

**為什麼不自動改寫**：自動改寫會讓使用者不知道自己看的是別的查詢的結果，
而且改錯的時候沒有回頭路。Google 這麼做是因為它有信心分數；我們沒有。

**驗收**：`?keyword=素時` 回 0 筆 ＋ `did_you_mean` 含「素食」；正常的詞不會產生建議
（避免每次搜尋都多跑一段）。
**反向驗證**：把 CJK 那條路換成 `levenshtein()`，中文的測試要紅。

### A5 — 搜尋範圍變成明確的控制項

**現況**：首頁關鍵字搜尋「不限目前範圍」、列表頁「跨全部城市」，兩頁行為不同，
都靠一行 `role="status"` 的小字解釋，而且**使用者改不了**。

**做什麼**：兩頁共用一個「搜尋範圍」三選一（寫進網址 `?scope=`）：

```text
map    目前地圖範圍（首頁預設；送 bbox＝目前 viewport）
city   這座城市（列表頁預設；送該城市 bbox）
all    全部城市（送不帶 bbox）
```

API **不用改**——`bbox` 參數已經支援這三種形狀，這是純前端的控制項與網址狀態。

**驗收**：首頁選「全部城市」後移動地圖，結果不再被 viewport 篩掉；重新整理後範圍
還在；分享網址對方看到同一個範圍。
**反向驗證**：拿掉 `scope` 的網址回填，上一頁測試要紅。

### A6 — 建議清單的鍵盤操作與 a11y

**現況**：候選只有 `@mousedown.prevent`，沒有鍵盤路徑，也沒有 combobox 語意。

**做什麼**：`role="combobox"` ＋ `aria-expanded`／`aria-controls`／
`aria-activedescendant`，清單 `role="listbox"`、每項 `role="option"`；
↑↓ 移動、Enter 選取、Esc 關閉、Tab 關閉並保留輸入。

**注意**：`@mousedown.prevent` 那一招（2026-08-26 實測到的 blur 競態）**要留著**，
鍵盤路徑是**加上去**的，不是取代它。

**驗收**：只用鍵盤能從輸入框走到第三個建議並選取。
**反向驗證**：拿掉 `aria-activedescendant` 的更新，對應測試要紅。

### A7 — 最近搜尋

輸入框 focus 且為空時，顯示最近 5 筆（`localStorage`，只存字串，可一鍵清除）。
**不做**熱門搜尋——那需要 A8 的資料先跑一陣子，而且會有隱私與冷啟動問題。

### A8 — 零結果查詢紀錄（下一輪同義詞表的依據）

**做什麼**：結果為 0 時寫一筆 `search_misses`（`keyword`、`normalized`、`result_count`、
`had_filters`、`created_at`）。**不記 IP、不記 user id、不記座標**——這是產品訊號，
不是使用者追蹤。加一個 `php artisan search:misses --since=7d` 列出 top N。

**為什麼**：這個 repo 每一輪都是「先量再改」，唯獨同義詞表是憑猜的。有了這張表，
下一輪加詞就有依據，而且 A4 的效果也才量得出來（錯字容錯上線後，miss 應該下降）。

**隱私**：關鍵字本身可能含地名，但不綁任何身分。保留 90 天，排程清舊資料。

### A9 — 效能天花板：先立 benchmark，不急著上 FULLTEXT

`KeywordSearch` 的註解已經寫明為什麼現在不上 FULLTEXT（權重不可控、資料量小），
這個判斷**維持**。要補的是一條會在變慢時變紅的線：

- 一條 benchmark 測試：seed 10 倍資料（約 12,000 筆），跑一個 8 變體的查詢，
  斷言 < 300ms。門檻放 config，超過就是「該回頭談索引了」的訊號。
- `restaurants.name` 加一般索引對 `LIKE '%…%'` **沒有幫助**（前綴萬用字元用不到索引），
  不要為了看起來有做而加。真的要動，選項是 MySQL ngram parser 的 FULLTEXT
  或外部搜尋引擎，那是獨立的一批工作。

## 三、搜尋畫面 UI/UX 改版（B0–B8）

範圍：`HomeView`、`SearchBox`、`FilterDrawer`、`RestaurantListView`、`RestaurantMap`。
**詳情頁、Admin、AI Office、登入註冊不動**（依 2026-09-03 使用者指示）。

### B0 — 先抽 design token（只抽這四塊用得到的）

**現況**：Tailwind 裝了幾乎沒用；`#2f855a`（header／按鈕）與 `#2f6b4f`（popup 按鈕）
是同一個綠的兩個值，灰階四五種散在各檔案。

**做什麼**：`resources/css/app.css` 加一組 CSS 變數（`--vm-green-600`、`--vm-orange-500`、
`--vm-ink-*`、`--vm-space-*`、`--vm-radius-*`、`--vm-shadow-*`），
**只把這五個檔案改成引用變數**，其他頁面維持原樣。

**為什麼是 CSS 變數不是 Tailwind class**：全站換成 utility class 是另一個量級的改動，
而且 Leaflet 插進 DOM 的 popup／tooltip 吃不到 Vue 的 scoped style（`app.css` 的註解
已經記錄這件事）——CSS 變數兩邊都吃得到，Tailwind class 不行。

**驗收**：改完後全域 grep 這五個檔案，硬編碼的 hex 只剩變數定義那一處。

### B1 — 首頁改成地圖優先版面

**現況**：hero（標題／標語／城市切換／搜尋框／定位鈕／關鍵字徽章／篩選抽屜）
在地圖**上方**堆成一疊，地圖被推下去。

**做什麼**：地圖佔滿可視區，控制項浮在地圖上：

```text
┌──────────────────────────────────────┐
│ [搜尋框 ............] [範圍▾] [篩選 3] │ ← 浮動列（固定在頂端，半透明底＋陰影）
│                                      │
│            地  圖  ＋  marker         │
│                                      │
│  [圖例]                    [📍 定位]  │ ← 角落控制項
├──────────────────────────────────────┤
│ ▁▁▁ 42 家 · 相關性 ▾           展開 ▴ │ ← 底部 sheet（收合時只有這一行）
└──────────────────────────────────────┘
```

「VeggieMap／找到適合你的素食餐廳」這個 hero 標題**移除**：使用者已經在站上了，
一個地圖產品的首屏應該是地圖。品牌留在 header。

**行動版**：底部 sheet 三段（收合 = 一行摘要／半開 = 看得到三張卡／全開 = 只有清單），
拖曳或點摘要列切換。桌機版則是左側清單 ＋ 右側地圖的兩欄。

### B2 — 地圖 ↔ 清單雙向連動

**現況**：首頁只有地圖，清單在另一頁；兩邊沒有任何關聯。

**做什麼**：
- 滑到卡片 → 對應 marker 放大＋提到最上層；離開 → 還原。
- 點 marker → sheet 捲到那張卡並高亮（popup 仍然保留，2026-08-27 才把它救活，不要又弄死）。
- 地圖移動 → 清單跟著換（沿用現有的 `bounds-changed` ＋ 請求序號防競態）。

**注意**：`RestaurantMap` 目前用 `markercluster`，cluster 收起來時個別 marker 不存在，
高亮要對 cluster 做（或在 highlight 時 `zoomToShowLayer`）。這是實作時最容易漏的一點。

### B3 — 篩選：常駐 quick filter ＋「更多篩選」

**現況**：六組 chip 平鋪在一個抽屜裡，沒有優先級。

**做什麼**：浮動列上常駐三個最常用的（**營業中** / **純素食店 ↔ 含友善店** /
**高可信度**），其餘（飲食類型細項、價位、8 個特色）收進「更多篩選」面板。
哪三個是「常用」不要用猜的——A8 上線後看實際使用率再定，**第一版就先用這三個並註明是暫定**。

面板改成底部 sheet（行動版）／側邊 panel（桌機），底部固定「清除全部」與
「顯示 N 家結果」——後者需要 B4。

### B4 — 每個篩選帶「會剩幾家」

按下去才知道剩幾家，等於每個 chip 都是一次賭博。做法是一次
`GET /restaurants/facets`（同一組條件、對每個候選值算 `COUNT(*)`），
chip 上顯示數字，**0 家的 chip 變灰但不隱藏**（隱藏會讓使用者以為功能不見了）。

**成本**：這是 N 次 count。**先量**：若超過 200ms，退而求其次只算常駐那三個 quick filter。
不確定值不值得就先做三個，別一次做 20 個。

### B5 — 載入狀態改 skeleton

現在是一行「載入中…」。改成三張卡片形狀的 skeleton（列表）／地圖上一層淡遮罩＋
spinner（地圖）。`aria-busy="true"` 要記得帶，不然讀螢幕使用者只會覺得畫面卡住。

### B6 — 空狀態要有可按的下一步

呼應 A3：空狀態不再是一段文字，而是
「這個範圍沒有符合的店」＋ A3 回來的放寬按鈕 ＋（有錯字建議時）A4 的「你是不是要找」。
**沒有可放寬的條件時**才退回現在的靜態文案——那時候「換個關鍵字」才是誠實的建議。

### B7 — 圖例補第三種，並修掉不一致

`markerIcon` 在 `venue_kind` 缺席時畫灰色 `unknown` marker，圖例只列兩種。
兩條路：把 `unknown` 加進圖例（「資料待確認」），或確保列表 API 一定帶 `venue_kind`
讓 `unknown` 不再出現。**先查哪一種情況真的會發生**（`RestaurantResource` 的
`venue_badge`／`venue_kind` 是 `$this->when(...)`，代表沒 eager load 就不會有）
——查完再決定，不要兩件事都做。

### B8 — 卡片資訊層級重排

**現況**：一張卡片把店名／徽章／料理／摘要／命中菜色／可信度／營業狀態／地址
全部平鋪成同一層的 `<span>`，全部一樣重。

**做什麼**：三層——
1. 店名 ＋ venue 徽章（純素食／素食友善，**形狀也不同**，不只顏色）
2. 一行事實：營業狀態 · 料理種類 · 距離（有座標時）
3. 一行證據：命中原因（A1）／可信度／地址

可信度改成三段標籤（高／中／待確認）而不是裸分數——0–100 的分數看起來像評分，
而這個產品**刻意不做評分**，兩者混淆是體驗上的傷害。

## 四、建議執行順序

一次做一項，做完跑測試、更新 [progress.md](progress.md)、commit push，不要一次全做。

```text
第 1 批（看得見、風險低）  A1 → A2 → B8 → B7
第 2 批（零結果的完整解）  A3 → B6 → A4
第 3 批（版面改動）        B0 → B1 → B2 → B3
第 4 批（要先有資料）      A8 →（觀察一週）→ B4 → A7
隨時可做（獨立）           A5、A6、A9
```

A8 排在第 4 批不是因為它不重要，而是因為它的產出要**時間**才有價值；
但它的實作很便宜，想提前做進第 1 批也可以——只是別期待馬上有資料可看。

## 五、明確不做

- 不做會員、評分、評論（2026-08-26 使用者指示），所以也不做「依評分排序」的 UI。
- 不做自然語言／AI 搜尋（總 Prompt 第四十三節列為 MVP 後）。
- 不做全站 UI 改版：詳情頁、Admin、AI Office、登入註冊這一輪不動。
- 不上 FULLTEXT／外部搜尋引擎（A9 說明理由），先立量測線。
- 不做熱門搜尋（要先有 A8 的資料，且有冷啟動與隱私問題）。
